# ADR-0001: Use runtime-config.yml for Runtime Build Configuration

Status: Accepted

## Context

The BiodiverseR runtime build process uses separate GitHub Actions
workflows for Windows, macOS, and Linux.

As runtime support expands across multiple operating systems, shared
build settings and platform-specific settings need to be managed
consistently.

A shared configuration source is needed to reduce duplication and make
it easier to manage runtime builder configuration across platforms.

## Decision

Use `.github/runtime-config.yml` as the authoritative source of runtime
build configuration.

GitHub Actions workflows will load configuration values from this file at
runtime using `yq`.

Shared configuration values and platform-specific configuration values
will be maintained in a single location.

Configuration is divided into a `globals` section for settings shared
across platforms and a `platforms` section for settings that may differ
between platforms.

Example configuration:

```yaml
globals:
  biodiverse:
    branch: master

  biodiverser:
    branch: main

  runtime:
    test_port: 3001

  build:
    no_alien_gtkstack: true

platforms:
  windows:
    perl:
      version: 5.38.4.1

  macos:
    perl:
      version: 5.38.4

    pkg_config_path: "/opt/homebrew/lib/pkgconfig"

    path: "/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin"

  linux:
    perl:
      version: 5.38.4
```

## Rationale

A shared configuration file provides:

- A single source of truth for runtime build settings.
- Reduced duplication across workflow files.
- Easier maintenance of runtime builder configuration.
- Improved consistency between Windows, macOS, and Linux runtime
  builders.
- Better visibility into the configuration used to build runtime
  artifacts.

Using `yq` allows workflows to consume YAML configuration without
requiring additional Python dependencies.

## Consequences

### Positive

- Runtime configuration is maintained in one location.
- Workflow files become simpler and easier to read.
- Shared settings can be modified without editing multiple workflows.
- Future platform support can reuse the same configuration structure.
- Release automation can consume the same configuration information.

### Negative

- Workflows now depend on the presence and structure of
  `.github/runtime-config.yml`.
- Changes to configuration may affect multiple platforms.
- Care must be taken when modifying shared settings.

## Alternatives Considered

### Store configuration directly in each workflow

Rejected.

This approach is simple initially but results in duplicated
configuration and increased maintenance effort.

### Use GitHub Actions environment variables only

Rejected.

This centralizes values within a workflow but does not provide a shared
configuration source across multiple workflows.

### Load configuration using Python and PyYAML

Rejected.

Although functional, it introduces an unnecessary dependency on PyYAML.
Using `yq` is simpler and relies on tooling already available on the
GitHub-hosted runners.

## Related Decisions

- Runtime artifacts generated by CI are identified using source commit
  SHAs.
- Runtime release artifacts use version-based naming derived from Git
  tags.
- Platform-specific runtime settings may be used where required by
  platform tooling or compatibility constraints.
